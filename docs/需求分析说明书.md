# 数据备份软件需求分析说明书

## 1. 引言

### 1.1 编写目的

本文档旨在明确《数据备份软件》的系统需求与规格边界，为最多由3名开发人员组成的研发团队提供清晰、无歧义的技术蓝图。本文档将作为后续系统架构设计、接口定义、代码编写以及基于 `gtest` 测试用例编写的唯一基准。

### 1.2 项目背景

本项目为《软件开发综合实验》的核心实战任务，要求团队经历从需求分析到最终交付的完整软件生命周期。系统聚焦于文件系统级的数据备份与恢复，重点考核软件的正确性、易用性、健壮性以及 Linux 环境下的系统级 C++ 编程能力。

### 1.3 受众说明

本文档的预期读者包括：开发团队成员、项目导师、负责最终验收与代码审查的助教及评审委员会。

## 2. 总体描述

### 2.1 用户特点

目标用户群体主要为具备一定计算机基础的系统管理员、开发者或高级用户。用户习惯于通过终端与系统交互，对命令行的执行效率和反馈信息的准确性有较高要求。

### 2.2 运行环境说明

- **宿主环境**：Windows 操作系统。
- **目标与交付环境**：基于 Docker 构建的标准化 Linux 容器。最终项目交付物必须包含完整的 `Dockerfile`，确保环境的一致性与可复现性。
- **交互接口**：系统采用纯命令行接口 (CLI) 运行，不提供图形用户界面 (GUI)。

### 2.3 设计与工具链约束

- **语言约束**：核心后台逻辑必须 100% 采用 C++ 编写，严禁使用 Python/Shell 等脚本语言实现任何业务逻辑。
- **工具链**：开发与调试均依托于 VSCode 远程容器开发模式 (Dev Containers)。构建系统强制使用 CMake 与 Make。代码版本控制采用 git。
- **质量保障**：
  - 代码规范需通过 `cpplint` 检查。
  - 单元测试需基于 `gtest` 框架覆盖核心逻辑。
  - 内存泄漏与越界访问需使用 `valgrind` 进行严格排查。
  - 性能瓶颈分析需借助 `gprof` 或 `perf`。

## 3. 核心功能用例分析

本章节定义系统的基础能力（对应基础评估 40 分）。

### 3.1 用例：目录树数据备份

- **前置条件**：源目录存在且当前用户具有读权限；目标路径所在的父目录存在且当前用户具有写权限。
- **输入**：源目录的绝对或相对路径；目标存储路径。
- **处理逻辑**：
  1. 系统解析输入路径，校验路径合法性。
  2. 采用深度优先 (DFS) 或广度优先 (BFS) 算法递归遍历源目录树。
  3. 逐一读取源文件数据，并在目标路径下按原有层级结构创建对应目录与文件。
  4. 将数据流完整写入目标文件。
- **输出**：终端打印备份进度（如文件数量/字节数）及最终成功/失败状态码。

### 3.2 用例：目录树数据还原

- **前置条件**：指定的备份源数据（目录或打包文件）存在且未损坏；目标恢复路径合法且具备写权限。
- **输入**：备份数据所在的路径；期望恢复到的目标目录路径。
- **处理逻辑**：
  1. 系统校验备份数据的完整性与合法性。
  2. 解析备份结构，在目标路径下逆向重构目录树。
  3. 将备份的数据内容准确写入到重构出的文件树中。
- **输出**：终端打印恢复操作的执行报告，包括恢复的文件总数与最终状态。

## 4. 扩展功能规格详解

为达成高分目标（扩展 71 分组合），系统将在 Linux C++ 底层实现以下高级特性。

### 4.1 特殊文件支持 (EX-01) - 10分

- **功能描述**：在遍历目录时，系统需正确识别并持久化特殊文件的拓扑与属性，而非盲目读取其内容。
- **技术表现**：通过 Linux `lstat()` 系统调用读取文件状态，利用宏（如 `S_ISFIFO`, `S_ISLNK`, `S_ISCHR`, `S_ISBLK`）进行精准分支处理。
  - **软/硬链接**：备份时使用 `readlink()` 获取指向路径并保存记录；还原时使用 `symlink()` 或 `link()` 重建。
  - **管道/设备文件**：记录其 `dev_t` 设备号，还原时使用 `mkfifo()` 或 `mknod()` 重新生成节点。

### 4.2 元数据支持 (EX-02) - 10分

- **功能描述**：实现“原样备份”，确保文件恢复后的属主、时间戳及读写执行权限与原文件完全一致。
- **技术表现**：依托 `stat` 结构体，提取 `st_uid`, `st_gid`, `st_mode`, `st_atim`, `st_mtim`。恢复阶段调用 `chown()` 恢复属主，调用 `chmod()` 恢复权限，调用 `utimensat()` 以纳秒级精度恢复访问与修改时间。

### 4.3 自定义备份 (EX-03) - 6分

- **功能描述**：支持用户通过参数传递筛选规则，仅对满足条件的文件进行备份。
- **技术表现**：在目录遍历逻辑中挂载过滤器模块。支持通过 C++11 `<regex>` 库实现基于文件扩展名（如 `*.cpp`）或路径特征（如排除 `build/` 目录）的模式匹配。

### 4.4 打包与解包 (EX-04) - 10分

- **功能描述**：消除碎文件带来的 I/O 开销与管理困难，将整个目录树序列化为单一二进制大文件。
- **技术表现**：设计自定义的二进制封包协议。文件结构设计为：`[全局文件头 (魔数+版本)] + [文件条目1 (元数据头+文件名长度+文件名+数据长度+数据内容)] + [文件条目2...] + [文件尾校验和]`。利用 `std::fstream` 的 `read/write` 方法进行大块内存的二进制拷贝。

### 4.5 压缩与解压 (EX-05) - 10分

- **功能描述**：在二进制打包协议之上，引入无损压缩算法，显著减小最终备份文件的磁盘占用。
- **技术表现**：集成 zlib 或 lz4 等 C/C++ 压缩库。在内存中以 Chunk（数据块）为单位，对读取的数据流进行实时压缩后再写入磁盘；解压时进行逆向操作，确保解压后的二进制数据流能无缝对接解包模块。

### 4.6 定时备份与淘汰机制 (EX-06) - 10分

- **功能描述**：允许用户设置周期性任务，系统在后台按设定时间自动执行备份，并包含基础的数据淘汰机制以防磁盘占满。
- **技术表现**：通过解析类似 cron 的时间表达式，结合 `<chrono>` 与 `<thread>` 实现定时触发器。淘汰机制需维护一个基于时间线或存储配额的队列（如 LRU 或 FIFO），当触发阈值时，自动调用 `remove()` 或 `std::filesystem::remove_all()` 删除旧有备份大文件。

### 4.7 实时增量备份 (EX-07) - 15分

- **功能描述**：利用 Linux 底层的 inotify 机制，作为后台守护进程运行，自动感知用户目录内文件的增删改变化，并以极低延迟触发自动增量备份。
- **技术表现**：
  - **守护进程化**：启动时调用 `daemon(0, 0)` 或执行标准 Double-Fork 流程脱离控制终端。
  - **事件监听**：直接调用 Linux 原生 `inotify` API (`inotify_init`, `inotify_add_watch`)，监听 `IN_CREATE`, `IN_DELETE`, `IN_MODIFY`, `IN_MOVED_FROM`, `IN_MOVED_TO` 等事件。
  - **增量同步**：事件触发后，仅针对变更的文件节点执行备份逻辑，避免全量扫描带来的性能损耗。

## 5. 非功能需求

### 5.1 内存安全与资源管理

- **零泄漏承诺**：系统必须通过 `valgrind --leak-check=full` 的严格测试。杜绝内存泄漏、野指针访问及未初始化内存读取。
- **RAII 规范**：对文件描述符 (File Descriptors)、动态内存及锁，必须全面采用 RAII (Resource Acquisition Is Initialization) 惯用法（如智能指针、`std::lock_guard`、自定义的 FD 包装类），确保异常发生时资源被安全释放。

### 5.2 性能与并发要求

- **I/O 优化**：在进行大文件打包与拷贝时，应设置合理的读写 Buffer Size（如 4KB-64KB），减少频繁的系统调用切换。
- **性能瓶颈消除**：核心路径必须经过 `gprof` 或 `perf` 采样分析，确保 CPU 周期未被无效的字符串拷贝或低效的容器遍历（如在深层目录树中错误使用按值传递）所消耗。

### 5.3 健壮性与异常处理

- **防御性编程**：面对无读权限的文件、无法解析的特殊符号链接或“磁盘空间已满 (ENOSPC)”等极端场景，系统需能捕获异常 (`try-catch` 或检查 errno)，打印规范的错误日志，并跳过当前节点继续执行，严禁程序直接崩溃 (Core Dump)。
- **防爆栈设计**：在处理极深层级的目录树遍历时，需评估函数调用栈风险，必要时将递归算法重构为基于 `std::stack` 或 `std::queue` 的迭代算法。

## 6. 命令行接口规范

系统提供统一的主命令 `cbackup`，通过子命令 (Sub-commands) 与选项 (Flags) 进行任务路由。

**核心 CLI 语法设计示例**：

- **基础备份**

  ```
  cbackup backup --source /path/to/src --dest /path/to/backup_dir
  ```

- **打包并压缩备份（带元数据与特殊文件支持）**

  ```
  cbackup pack -z -m --source /path/to/src --dest /path/to/archive.cbk
  ```

  *(注：`-z` 启用压缩，`-m` 保留元数据)*

- **自定义过滤备份**

  ```
  cbackup backup --source /path/to/src --dest /path/to/dest --exclude "*.tmp" --include "*.cpp"
  ```

- **还原解包**

  ```
  cbackup restore --file /path/to/archive.cbk --dest /path/to/recover_dir
  ```

- **启动实时守护进程**

  ```
  cbackup daemon --watch /path/to/src --sync-to /path/to/dest --log /var/log/cbackup.log
  ```

- **配置定时任务**

  ```
  cbackup cron --schedule "0 2 * * *" --source /path/to/src --dest /path/to/dest --keep 5
  ```

  *(注：每天凌晨2点执行，保留最近5份备份)*

## 7. 版本控制与团队协作规范

为保障开发团队能够高效协作并避免代码合并冲突，本项目统一采用 Git 进行版本控制，并以 GitHub 作为中心代码托管平台。

### 7.1 核心分支策略

团队采用轻量级的并行分支模型：

- **`main` 分支**：主干分支。仅存放经过完整单元测试、随时可编译交付给助教验收的稳定版本代码。禁止直接向此分支 `commit` 代码。
- **`dev` 分支**：开发集成主分支。团队成员完成的功能模块经本地测试无误后，统一合并至此分支，作为每日协作的基准代码。
- **`feature/\*` 分支**：功能特性分支。每当着手开发独立新功能（如 `feat/compress`, `feat/inotify`）时，需从最新的 `dev` 分支拉取。开发完毕后通过 Pull Request (PR) 或直接合并回 `dev` 分支。

### 7.2 提交流程与规范 (Commit Conventions)

代码提交必须附带结构化的说明信息，遵循以下前缀以方便问题回溯：

- `feat:` 增加新功能或实现新需求（例：`feat: 实现对符号链接和管道文件的识别与备份`）。
- `fix:` 修复运行时 Bug 或逻辑缺陷（例：`fix: 解决源目录权限不足时导致的内存越界崩溃`）。
- `refactor:` 代码重构，不增减业务功能（例：`refactor: 优化 DFS 目录遍历的函数入参设计`）。
- `docs:` 补充或修改项目文档（如 README 或是需求说明书）。
- `test:` 新增或修改 `gtest` 测试用例。

### 7.3 日常协作工作流

1. **同步基准代码**：每日开发前，在本地终端执行 `git checkout dev` 和 `git pull origin dev`，确保获取队友提交的最新代码。
2. **隔离开发**：执行 `git checkout -b feature/任务名` 创建并切换至个人分支，在 Docker 的 Linux 容器内进行 C++ 编码与调试。
3. **小步提交**：完成一个小模块后，及时执行 `git add .` 与 `git commit -m "..."`，杜绝积攒一周代码后进行巨型提交。
4. **合并推送**：当前功能开发完成后，切换回 `dev` 分支再次 `pull` 拉取，解决可能产生的文件冲突后，将功能分支合并入 `dev`（`git merge feature/任务名`），最后执行 `git push origin dev` 推送至 GitHub。

### 7.4 工程环境忽略配置 (.gitignore)

结合 C++ 与 Docker 编译环境，项目根目录必须配置严谨的 `.gitignore` 文件，以防将冗余文件推入中心仓库：

- **编译中间产物**：强制忽略所有 `.o`, `.out`, `.so`, `.a` 文件及 `CMakeCache.txt` 等 CMake 缓存。
- **可执行文件**：忽略最终生成的 `cbackup` 命令行程序。
- **测试冗余数据**：绝对忽略在测试过程中产生的备份包（如 `*.cbk`）、海量测试碎文件日志等，防止撑爆 GitHub 仓库限制。
- **宿主机环境配置**：忽略 Windows 下 VSCode 自动生成的 `.vscode/` 目录（除非团队共用统一的 `devcontainer.json` 配置）。

### 7.5 冲突避免原则

- **架构解耦分工**：这是防止冲突的最优解。团队成员应分别负责独立的 `.cpp` 模块（如：成员A负责打包/压缩模块，成员B负责 inotify 监控，成员C负责 CLI 参数解析），从物理文件层面避免多人在同一行代码上发生冲突。
